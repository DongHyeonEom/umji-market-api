## 진행 규칙

- `[ ]`는 미완료, `[x]`는 실제 코드·문서 반영과 필요한 검증까지 완료된 상태
- Task 일부만 완료된 경우 체크 상태를 유지하며 `todo.md`에 남김. 모든 수용 기준이 완료되면 Task 전체를 `completed-todo.md`로 이동
- 서비스 코드를 착수·수정하기 전에 관련 `docs/services/<service>.md`의 Mermaid 알고리즘 흐름과 수용 기준을 먼저 확정
- 각 Task를 `서비스 개발`과 `서비스 자동화 테스트 개발 및 테스트`로 나눠 추적
- 범위가 없으면 체크리스트에 항목 및 수용 기준을 추가한 뒤 구현
- 테스트를 작성했더라도 실행하지 않았거나 결과를 확인하지 못한 항목은 `[ ]` 유지
- 정책 미확정 항목은 임의로 확정하지 않고 설계 결정 항목으로 유지
- 구현 중 정책·운영 절차·외부 연동 제약이 발견되면 관련 수용 기준을 먼저 갱신하고 검토 지점에서 결정 확인
- Task의 개발·테스트가 완료되면 동일 feature 브랜치에 수용 기준별 커밋·push 후 feature 단위 PR 하나로 제출
- 공통 완료 기준은 개별 미완료 작업이 아니라 각 Task에 적용하는 완료 규칙으로 관리

## Task 22 — 관리자 거래 검색·브랜드별 운송비 정산 조회·변경 감사

관리자 초기 운영 메뉴에서 거래를 기간·조직·주문자·결제·배송 조건으로 찾고, 브랜드별 월간 운송비 근거를 조회할 수 있도록 API 기능 보완. 화면 메뉴와 View Flow는 작업 공간의 `umji-market-design/admin-view-flow.md` 기준.<br>
배송 운송비는 구매자에게 청구하지 않고 판매자 부담 비용 데이터로 취급. 이 Task는 조회·집계까지이며 지급·차감 확정 기능은 별도 정책 결정 전 제외.<br>

### 서비스 개발

- [x] 필수 주문일 시작일·종료일, 구매자 Organization명, 주문자명, 결제 상태, 배송 상태 및 선택 주문번호 조건의 관리자 거래 검색 API 구현
- [x] 주문 시각(KST) 기준 검색 기간·최신순 페이지네이션, 주문 상세의 품목·결제·배송 송장·세금계산서 상태 및 개인정보 최소화 구현
- [x] 브랜드와 월 조건으로 송장 등록일(KST) 기준 실제 운송비 합계·송장 수·택배사별 합계·미등록 수 및 송장·주문·품목 상세 조회 API 구현
- [x] 운송비 조회에서 구매자 청구 금액과 분리하고 브랜드 범위를 서버에서 검증
- [x] 결제 상태·송장번호·배송 상태·실제 운송비·세금계산서 결과 변경 시 처리자·시각·변경 전후 업무 값·사유를 운영 이력에 기록
- [x] 감사 이력에 저장할 필드를 제한하고 기존 운영 감사 로그 검색·보존 정책과 정합성 유지

- [x] 서비스 흐름도·API 계약·권한·DB 문서 및 구현 현황 갱신

### 구현 전 설계 결정

- 송장 등록일(KST)을 월 귀속 기준으로 사용하고 현재 실제 운송비를 합산. 미등록 비용은 합계 제외 및 건수 표시
- 운송비 정산은 조회·집계만 제공. 지급·차감·정산 확정은 범위 제외
- 거래 검색 기간은 필수 시작일·종료일, Organization명·주문자명 부분 일치, 목록 연락처 뒤 4자리 표시
- 결제 상태·실제 운송비 변경은 사유 필수. 감사 조회 권한은 기존 `ADMIN_AUDIT_READ` 범위 유지
